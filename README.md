# DevOps Assessment: Terraform + Database Reliability

AWS infrastructure written in Terraform (plan only, nothing is deployed) and a local
PostgreSQL setup with migrations, seed data, an index, and backup/restore scripts.

```
Internet -> ALB -> ECS Fargate -> RDS PostgreSQL
```

## Repo layout

```
.
├── docker-compose.yml
├── db/
│   ├── migrations/001_create_tables.sql

│   ├── modules/{network,ecs,rds}
```

## Part 1 and 2: Terraform

### What it creates

| Module | Resources |
|---|---|
| `network` | VPC, 2 public + 2 private subnets, internet gateway, NAT gateway(s), route tables, ALB / ECS / RDS security groups |
| `ecs` | ECS cluster, CloudWatch log group, IAM roles, Fargate task definition (nginx placeholder), ALB + target group + listener, ECS service |
| `rds` | DB subnet group, RDS PostgreSQL instance |

### How RDS is kept private

- RDS is in the private subnets and `publicly_accessible = false`.
- The RDS security group has one ingress rule: port 5432 from the **ECS security group**.
  There are no CIDR based rules and no egress rules.
- The ECS security group only accepts the app port from the ALB security group.
- The ALB security group is the only one open to the internet (port 80).
- The master password is generated by RDS (`manage_master_user_password`) and stored in
  Secrets Manager. ECS reads it through the task execution role, so no password is in the code.

### dev vs prod

| Setting | dev | prod |
|---|---|---|
| VPC CIDR | 10.10.0.0/16 | 10.20.0.0/16 |
| NAT gateways | 1 (shared) | 1 per AZ |
| ECS task size | 256 CPU / 512 MB | 512 CPU / 1024 MB |
| ECS task count | 1 | 2 |
| RDS instance | db.t4g.micro | db.m6g.large |
| RDS multi-AZ | false | true |
| RDS backup retention | 3 days | 30 days |
| Deletion protection | false | true |
| State | `s3://hotel-terraform-state-dev/dev/...` | `s3://hotel-terraform-state-prod/prod/...` |

Each environment folder has its own `variables.tf`, `terraform.tfvars` and `backend.tf`.

### Validate locally (no AWS account needed)

You need Terraform >= 1.10.

```bash
cd infra/envs/dev          # or prod

terraform fmt -check -recursive ../..
terraform init -backend=false
terraform validate

# the S3 state buckets in backend.tf are placeholders, so use a local backend for review
printf 'terraform {\n  backend "local" {}\n}\n' > backend_override.tf
terraform init -reconfigure
terraform validate

terraform plan -refresh=false -var plan_only=true

rm backend_override.tf    # when done
```

`backend_override.tf` replaces the S3 backend with a local one, only for this check
(it is git-ignored). For a real deployment, create the bucket first and run a normal
`terraform init` without that file.

After the first `terraform init`, commit the generated `.terraform.lock.hcl`.

### Notes

- The ALB only has an HTTP listener. For real production add an certificate and an
  HTTPS listener with an HTTP redirect.
- `deletion_protection` in an environment also turns on ALB deletion protection and makes
  RDS take a final snapshot when destroyed.

## Part 3: GitHub Actions

`.github/workflows/terraform.yml` runs on pull requests that touch `infra/**`, once for
`dev` and once for `prod`. Steps: `terraform fmt -check`, `init`, `validate`, `plan`.

The plan is shared in three places: a PR comment, the job summary, and a downloadable
artifact (`tfplan-dev`, `tfplan-prod`). It uses dummy AWS credentials and `plan_only`,
so no real AWS account is needed.

## Part 4, 5 and 6: Local database

Start the database (runs the migrations and the seed on first start):

```bash
docker compose up -d
```

Optional: copy `.env.example` to `.env` to change user, password, database name or port.
The defaults are `postgres` / `postgres` / `hotel_db` on port 5432.

### Tables

`hotel_bookings` and `booking_events` are created in `db/migrations/001_create_tables.sql`,
using the schema from the assignment.

### Seed data
`db/seed/seed.sql` inserts 100 bookings across 5 organizations, 6 cities (delhi has the
most rows), and 4 statuses (confirmed, pending, cancelled, completed). Booking dates are
spread over the last 60 days. Every booking has a `booking_created` event, and every
booking that is not `pending` also has a `status_changed` event.

Check it:

```bash
docker compose exec db psql -U postgres -d hotel_db -c \
  "SELECT city, count(*) FROM hotel_bookings GROUP BY city ORDER BY 2 DESC;"
docker compose exec db psql -U postgres -d hotel_db -c \
  "SELECT count(*) FROM booking_events;"
```

### Index and why

```sql
CREATE INDEX idx_hotel_bookings_city_created_at
    ON hotel_bookings (city, created_at)
    INCLUDE (org_id, status, amount);
```


The query filters on `city = 'delhi'` (equality) and `created_at >= NOW() - 30 days` (range),
then groups by `org_id, status` and sums `amount`.

- `city` is first because equality columns should come before the range column.
- `created_at` is second so Postgres can read just the last 30 days for that city
  as one continuous range of the index.
- `org_id`, `status` and `amount` are added with `INCLUDE`. They are not used for searching,
  but being in the index means Postgres does not need to read the table at all
  (index-only scan).

See the plan:

```bash
docker compose exec db psql -U postgres -d hotel_db -c "
EXPLAIN (ANALYZE, BUFFERS)
SELECT org_id, status, COUNT(*), SUM(amount)
FROM hotel_bookings
WHERE city = 'delhi'
  AND created_at >= NOW() - INTERVAL '30 days'
GROUP BY org_id, status;"
```

The seed is only 300 rows, so Postgres may still choose a sequential scan because that is
cheaper for a tiny table. To see that the index is usable, force it:

```bash
docker compose exec db psql -U postgres -d hotel_db -c "
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT org_id, status, COUNT(*), SUM(amount)
FROM hotel_bookings
WHERE city = 'delhi'
  AND created_at >= NOW() - INTERVAL '30 days'
GROUP BY org_id, status;"
```

You should see `Index Only Scan using idx_hotel_bookings_city_created_at`.

### Backup

```bash
./scripts/backup.sh
```

Creates `backups/hotel_db_<YYYYMMDD_HHMMSS>.sql.gz` using `pg_dump`.

### Restore

```bash
./scripts/restore.sh                                  # uses the newest backup
./scripts/restore.sh backups/hotel_db_20250101_120000.sql.gz   # or pick one
```

The script drops and recreates a **fresh** database called `hotel_db_restored`
(change it with `RESTORE_DB=name`), loads the dump into it, and prints the row counts of
both tables for the original and the restored database.

### How to verify the restore worked

1. The script prints counts like this, and the two numbers on each line must match:
   ```
   hotel_bookings : 100 vs 100
   booking_events : 540 vs 540
   ```
2. Check the data and the index in the restored database yourself:
   ```bash
   docker compose exec db psql -U postgres -d hotel_db_restored -c "\dt"
   docker compose exec db psql -U postgres -d hotel_db_restored -c "\di"
   docker compose exec db psql -U postgres -d hotel_db_restored -c \
     "SELECT org_id, status, COUNT(*), SUM(amount) FROM hotel_bookings WHERE city = 'delhi' GROUP BY org_id, status;"
   ```
3. Optional full proof: delete data from the original and confirm the restored copy still has it:
   ```bash
   docker compose exec db psql -U postgres -d hotel_db -c "DELETE FROM booking_events; DELETE FROM hotel_bookings;"
   docker compose exec db psql -U postgres -d hotel_db_restored -c "SELECT count(*) FROM hotel_bookings;"
   ```

### Reset everything

```bash
docker compose down -v      # removes the container and the data volume
```
